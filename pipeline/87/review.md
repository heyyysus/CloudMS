# Plan review — issue #87

## Findings

- **Scope matches the issue.** The issue asks for the policy-level Accounting subtab to become a ledger with a running balance, positive when owed / negative as credit. The plan delivers exactly that (summary + chronological table + running balance), stays frontend-only, and doesn't creep into client-level accounting, exports, or aging buckets (explicitly out of scope). No backend files touched, consistent with "Touches backend: No."
- **Honest handling of the unreachable-credit case.** Spot-checked: a payment's `amountApplied` is what's applied to the invoice, with any excess as `changeGiven` handed back rather than held (`frontend/src/api/payments.ts`), so `sum(charges) - sum(credits)` can't go negative today. The plan calls this out explicitly instead of silently building around it or overclaiming the feature is fully done, and correctly scopes "hold overpayment on account" as a separate backend issue. This is the right call rather than a defect.
- **Direction fits PROJECT.md.** Accounting (invoices, payments, receipts, trust ledger) is listed as already built; this is a presentation-layer upgrade over existing data, not a new pillar or roadmap jump. Doesn't touch the Home dashboard (roadmap item 1) or any of the not-yet-built pillars.
- **File list and API claims verified.** `GET /invoices?policyId=` and `GET /payments?policyId=` both exist in `docs/API.md` (confirmed lines 541, 561). `frontend/src/api/payments.ts` indeed lacks a list function today — only `recordPayment`/`voidPayment`. `frontend/src/components/ui/table.tsx` does not exist yet, so vendoring it is a real addition, and `docs/frontend-ui-design.md` line 10 does explicitly defer TanStack Table — the plan's plan to vendor only presentational `Table` primitives (no sorting/pagination) is consistent with that deferral rather than undermining it.
- **Void/ledger semantics check out.** Confirmed against `backend/src/repositories/payments.ts` (`voidPayment` stamps `voidedAt`/`voidedBy`/`voidReason` on the row, reopens the invoice) and `backend/src/repositories/invoices.ts` (`voidInvoice` voids open payments) — there is no separate reversal row at this layer, matching the plan's description of emitting the original + a `*_void` row with zero effect.
- **Correctly identifies its own highest-risk detail.** Spot-checked `invoice-payment-dialog.tsx`'s existing `invalidateQueries` calls: it invalidates `['invoices','byClient', client.id]`, `policyLogs`, `policyAttachments` — but nothing for payments. The plan's new `['payments','byPolicy', policyId]` key is correctly flagged (Risk #2) as needing invalidation added on the payment record/void paths, or the ledger goes stale after a payment. This is real and worth the implementer's attention, but it's a concrete, scoped fix, not a soundness problem with the plan.
- **Reuses existing patterns well.** Keeps the invoices query on the existing shared `['invoices','byClient', clientId]` key with client-side policy filtering (matching `ClientInvoices`'s existing, commented rationale), reuses `InvoicePayment` type rather than inventing a new shape, follows the `request(...)` + `signal` pattern, and preserves the sibling-buttons-never-nested convention from `client-invoices.tsx`.
- **Tests are adequate for a frontend-only change.** Plan uses the repo's actual test conventions: plain Vitest unit tests for the pure ledger builder (`lib/*.test.ts`) and Storybook-as-tests via Vitest browser mode for the component, matching `client-invoices.stories.tsx`. No backend changes, so `TestContext` fixtures don't apply here — correctly noted as "no backend test run needed." Reasonable edge cases enumerated (voided invoice/payment, `changeGiven`, tie-break ordering, empty state).
- **Security/data exposure: no new surface.** No new endpoints, no new auth paths, no new user input parsed beyond what's already fetched and rendered from existing authenticated endpoints. Money handled via integer cents per existing `lib/money.ts` convention, avoiding float/string-compare bugs.
- **Minor, non-blocking judgment calls flagged transparently rather than hidden:** newest-first vs. oldest-first display inconsistency with the rest of the screen, double-row void rendering vs. single struck-through row, and optional deletion of `client-invoices.tsx` — all explicitly left open for reviewer/implementer discretion rather than asserted as settled.
