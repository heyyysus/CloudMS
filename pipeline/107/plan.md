# Backend Vitest coverage metric in CI (report only, no threshold)

## Goal

`cd backend && npm run test:coverage` produces a coverage report (text summary on
stdout, `backend/coverage/coverage-summary.json`, `backend/coverage/lcov.info`),
and the `backend` job in `.github/workflows/ci.yml` runs that script instead of
`npm test`, publishes the numbers to the PR (comment + job summary) and uploads
`lcov.info` as an artifact.

Hard requirement: **coverage must never fail the build on its own.** No
`thresholds` key in the Vitest config, and the reporting steps must not be able
to turn a green test run red (see Risks — this needs `continue-on-error` on the
comment step, which the issue body does not mention).

Done also means `npm run lint` and `npm run format:check` still pass with a
populated `coverage/` directory in the tree.

## Approach

1. **Install the provider.** In the worktree: `cd backend && npm i -D
   @vitest/coverage-v8@4.1.10 --legacy-peer-deps`. The version must match the
   installed vitest exactly — `package-lock.json` resolves
   `node_modules/vitest` to `4.1.10`, and `@vitest/coverage-v8` peer-depends on
   the identical vitest version. Confirm both `package.json` and
   `package-lock.json` changed.

2. **`backend/vitest.config.ts`** — the file today is only
   `{ test: { environment: "node", include: ["src/**/*.test.ts"] } }`. Add
   `coverage` inside `test`, exactly as specified in the issue:

   ```ts
   coverage: {
     provider: "v8",
     reporter: ["text-summary", "json-summary", "lcov"],
     include: ["src/**/*.ts"],
     exclude: [
       "src/**/*.test.ts",
       "src/routes/testHelpers.ts",
       "src/db/seed.ts",
       "src/db/seed/**",
       "src/scripts/**",
       "src/index.ts",
       "src/types/**",
     ],
     reportsDirectory: "coverage",
   }
   ```

   Deviation from the issue body, deliberate: the issue lists
   `"src/db/migrations/**"`, but **that directory does not exist** — Drizzle SQL
   migrations live in `backend/drizzle/` (not `.ts`, so never matched by
   `include`) and the migrator is `src/db/migrate.ts`. Dropping a dead glob is
   safe; keeping it would just be noise. Conversely the seed is *both*
   `src/db/seed.ts` and a `src/db/seed/` directory (`run.ts`, `wipe.ts`,
   `households.ts`, …), so `src/db/seed/**` is added alongside the file the
   issue named — otherwise seven untested seed modules drag the number down for
   no signal. Leave `src/db/migrate.ts` **in** scope (it is real, exercised
   startup code); if the reviewer disagrees, excluding it is a one-line edit.

   No `thresholds` key. Note that Vitest's `coverage.all` defaults to true, so
   the `include` glob means source files with zero tests still appear in the
   report at 0% — that is the point of the metric.

3. **`backend/package.json`** — add `"test:coverage": "vitest run --coverage"`
   next to the existing `"test": "vitest run"`. Keep `test` as-is so local runs
   and any other caller stay fast.

4. **Lint/format ignores.** The `lcov` reporter emits an HTML report
   (`coverage/lcov-report/` with `block-navigation.js`, `prettify.js`,
   `sorter.js`) alongside `lcov.info`, and `npm run lint` is a bare `eslint .`
   that will happily lint those generated `.js` files. Add `"coverage/**"` to
   the `ignores` array in `backend/eslint.config.js` — ESLint flat config does
   **not** read `.gitignore`. Prettier 3 *does* default `--ignore-path` to
   `.gitignore` + `.prettierignore` and `backend/.gitignore` already has
   `coverage/`, so `format:check` is likely already safe; add `coverage/` to
   `backend/.prettierignore` anyway to make it explicit and independent of that
   default. Verify both claims by running the two scripts with `coverage/`
   present (step 7).

5. **`.github/workflows/ci.yml`, `backend` job.**
   - Replace `- run: npm test` (line 71) with `- run: npm run test:coverage`.
     Leave the preceding `npx ts-node src/db/migrate.ts` step and the following
     `npm run build` untouched — the suite hits the real Postgres service
     container and still needs the migrated schema.
   - Add a job-level `permissions:` block. A job-level block **replaces** the
     workflow defaults rather than merging, so it must spell out what the job
     already relies on:

     ```yaml
     permissions:
       contents: read
       pull-requests: write
     ```
   - After the test step, add:

     ```yaml
     - uses: davelosert/vitest-coverage-report-action@v2
       if: github.event_name == 'pull_request'
       continue-on-error: true
       with:
         working-directory: backend
         json-summary-path: coverage/coverage-summary.json
         file-coverage-mode: changes
     ```

     Two deviations from the issue body, both in service of "never fails the
     build": `continue-on-error: true` (a fork PR gets a read-only
     `GITHUB_TOKEN`, so the comment POST 403s and would otherwise fail the job),
     and the `pull_request` guard (`file-coverage-mode: changes` and the comment
     itself have no meaning on a `push` to `main`). The issue's "keep
     `if: always()` off" instruction is honoured — the step still only runs when
     the test step passed.
   - Then, unconditionally:

     ```yaml
     - uses: actions/upload-artifact@v4
       with:
         name: backend-coverage
         path: backend/coverage/lcov.info
         retention-days: 7
     ```

     Path is repo-root-relative on purpose: `defaults.run.working-directory`
     applies only to `run` steps, not to action inputs. This is what makes the
     number inspectable on `main` pushes, per the issue.
   - The `changes` path filter already lists `.github/workflows/ci.yml` and
     `backend/**`, so the PR self-triggers the backend job. No filter edit.

6. **Do not** add a coverage step to `.github/workflows/frontend.yml` — out of
   scope, and the frontend suite isn't in CI at all yet (PROJECT.md names that
   as a separate gap).

## Risks / open questions

- **Fork PRs.** `pull-requests: write` is not granted to `GITHUB_TOKEN` on
  pull requests from forks; the report action's comment POST will 403. Mitigated
  by `continue-on-error: true`. Without it, this issue's own "must never fail
  the build" requirement is violated for every fork PR — this is the one place
  the plan intentionally departs from the issue's step 4.
- **First-run baseline.** `file-coverage-mode: changes` diffs against a base
  coverage report the action fetches from the target branch. On the very first
  PR there is no base on `main` yet, so expect a comment with no delta column.
  Not a failure; don't chase it.
- **v8 provider vs. ts-node/esbuild transforms.** Vitest 4's v8 provider does
  AST-aware remapping through the transform pipeline. Line attribution in
  decorator-heavy or heavily-transformed files can look slightly off. Since
  there is no threshold, cosmetic misattribution is acceptable; if the summary
  looks obviously wrong (e.g. a well-tested route at 0%), say so in the PR
  rather than silently switching provider.
- **Runtime.** `--coverage` adds instrumentation overhead to a suite that is
  already DB-bound. If CI wall-clock grows unacceptably, the fallback is to run
  coverage only on `pull_request` and keep plain `npm test` on `push` — but
  that loses the `main` artifact, so only do it if the slowdown is real. Measure
  before and after in step 1 of Tests.
- **`src/db/migrate.ts` in scope** — flagged in Approach step 2. Reviewer's
  call; trivially reversible either way.
- **Open question:** should `src/jobs/**` (scheduler) be excluded? It is
  disabled under `DEMO_MODE` (see recent commits) and may report low coverage
  that is not meaningful. Leaving it **in** for now — a low number on real code
  is information, not noise, and there is no gate to trip.
